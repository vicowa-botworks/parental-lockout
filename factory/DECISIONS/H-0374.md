- Why: the retry-only fix loses to the measured class twice over. Fixture rows on curl 8.18.0: the
  step's old flags took a mid-body RST at rc 56 on ONE connection — zero retries spent, because
  `--retry` alone re-scores HTTP transients and a reset is transport — while adding
  `--retry-all-errors` spent FOUR; and the same old flags retried an HTTP 503 four ways, so the
  machinery was live and the error class is the whole story. Host-list-only loses because the
  shellcheck fetch has no sibling host to fall back to (one host, github.com), so for that fetch
  transport retry is the only repair available at all; tz-only scope loses because the shellcheck
  fetch carries the identical `--retry 3` against the same transport, and repairing the same line
  in both jobs cost one line each and did not move the anchored `H-0267` pointer into `ci.yml` —
  the edit holds the line count neutral above it by design. Skipping the leg loses what #469
  itself recorded as NOT established: the runner's curl build was never measured, and a fix for
  a transport error class is build-dependent — the leg makes every CI run print the number (this
  box: rc 1, six connections = one plus the five shipped retries, against the control's one). What
  the combination pays: ~25 s of retry-delay sleeps in the probe leg, unwrapped on purpose because
  it is the shipped shape, and up to ~12 capped attempts per half if BOTH hosts hang — red for a
  real archive-wide outage is honest, red for one degraded hostname is not. Fallback-after-failure
  with the digest gate unchanged means a fallback can only ever re-deliver the pinned bytes; the
  served-by line on success names which host delivered, so a future red run names the degraded
  host instead of guessing one.
