- Why: scrubbing is a list of names, and the incident is exactly a name missing from that list —
  the preamble already scrubs four, and it still let this one through (#449 and #425 each grew
  the list after their own leak). A pin is the same defence with the polarity inverted: `env`
  takes last-wins, so a value pinned at the end of the shipped list beats ANY inherited value,
  including names nobody has thought to unset yet — the scrub stays as hygiene, but containment
  no longer depends on remembering. The pin must sit in the shipped list and not in
  `proc_extra_env` because that array is appended AFTER the list by design (it is the leg's
  override channel); a pair carried there is overridable by the next `proc_extra_env` line,
  which is where the tick's poison would land — hence the shape leg forbids the array carrying
  `FACTORY_SERVICE_UNIT` at all, and legs that need a planted unit travel on
  `proc_units_dir`/`proc_service_unit`, two knobs that expand before the shipped assignments.
  `systemd-run` loses on access, not taste: the suite runs where no user manager exists for the
  agent user, and a fixture that cannot run proves nothing. What lost besides scrubbing-by-name:
  one leg at a time (every future pass would re-invent its own guard and miss the ones behind
  it) and trusting `--dry-run` fixtures (the defect was a write; a rehearsal cannot catch a
  write, and r342's live-FF legs are why the family runs real `git` at all).
