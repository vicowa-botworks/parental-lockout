## D-0100 · #525: `sudo make install` stops paying the delivery gate; the guarantee moves to `make verify install`

- Refs #525 -- finished by this entry's pull request, which carries the closing keyword; the only step left on the ticket is the supervisor's merge.
- Question: #525 reports, verbatim, "sudo make install takes a long time and seems to go
  through the factory decisions. sudo make install should just install parental-lockout why
  is it doing anything with the factory code?" The report is accurate and the cause was
  deliberate: the target carried `verify` as a prerequisite under a comment that argued the
  case ("Installing an unverified build means the machine that is about to enforce tonight
  is running a binary the repo's own gate would have rejected"), and the battery prints
  steps like `==> decision log` and `==> factory dirt verdict` before any file is copied.
  So the ticket reopens a decided question, and the person reopening it is the maintainer
  who owns the decision. Four shapes answer it — which one?
- Options: keep the prerequisite and document the cost, the operator pays minutes either way | install depends on a new product-only gate target that drops the harness steps but keeps the race tests | install depends on build alone, and the full gate stays one ordered command away as `make verify install` | install keeps the prerequisite behind a named opt-out the operator sets to skip it
- Chose: install depends on build alone, and the full gate stays one ordered command away as `make verify install`
- Why: the product-only subset fails the ticket on measurement, not taste: the race battery
  alone spent 77 s on `internal/schedule` and 63 s on `internal/web` in the 24 Nov run, so
  the subset is still minutes, and minutes is the complaint. The named opt-out is the shape
  this Makefile itself indicts where it keeps the mutant battery out of the gate — "a gate
  that slow gets skipped" — and a spelled-out bypass is a habit, not a guarantee; #525
  proves the operator reaches the skip anyway. Tie-break 6 (what the surrounding code
  does) cannot hold a prerequisite against the owner of the surrounding code, stated in
  their own issue; tie-break 4 is a three-file tie and decides nothing between the arms;
  tie-break 5 picks the shape: one `git revert` of the commit carrying this entry's trailer
  restores the prerequisite whole. What lost, stated as lost: a bare `sudo make install`
  no longer refuses a build the gate would reject — the README and the setup page now print
  the ordered-command form on the very page that lost the automatic guarantee, and the
  comment over the target keeps the measurement the prerequisite was worth. The automated
  paths that need a verified artifact keep verifying themselves, measured before the edit
  rather than argued: no CI job invokes the install target (`grep -rn` for it over
  `.github/workflows/` answered empty), packaging stages `deploy/install.sh` directly under
  DESTDIR, and `run-dev` keeps its `verify` prerequisite because the gate is the point of
  that loop and #525 names neither. One environment disclosure, because it bears on every
  gate number quotable from this box and on the base being red here before any byte of this
  unit changed: the host carries tzdata 2026f while CI installs the pinned 2026e pair
  against which `internal/schedule` certifies its DST bounds, and the widened-day walk
  refuses on Havana under 2026f (Havana's 2026 fall-back is no longer an ambiguous next
  midnight, so the candidate-zone guard fires exactly as designed). Reproduced both ways on
  24 Nov with the pinned pair fetched through CI's own digests and unpacked to scratch:
  rc 0 with `ZONEINFO` at the pinned 2026e tree, rc 1 with the host's 2026f as control.
  Following tzdata is the pin re-cut the pin's own entry assigns to a maintainer, not a
  unit's move; nothing here changes the pin, and the gate run for the pull request is taken
  against the pinned database with `ZONEINFO` aimed at it.
- Effect: the install target's prerequisites changed (`verify` out, `build` in, the internal
  `$(MAKE) build` call deleted with its job now done by the prerequisite) and its comment
  rewritten with the measurement and the ordered-command form; the README "From source"
  section and the setup page's build-and-install section replace their "runs the repo's
  gate first" sentences with the ordered-command sentences; gate verdicts are quoted in the
  pull-request body from the runs that produced them, never here (#1180).
- Checkpoint: 0629bd7
- Correction 24 Nov: `D-0102` measured that the ordered-goal form `make verify
  install` this entry shipped holds only for a serial make: with `-j`, `-k` or a job count in
  `MAKEFLAGS` the two goals are independent and the installer ran while the gate refused. The
  decision, the loss statement and the rollback stand as written; the guarantee now rides the
  named target `install-verified`, whose `verify` prerequisite edge make must keep under
  parallelism. See `DECISIONS/D-0102.md`.
